## 验证目标

嵌入式验证需要逐层回答不同问题：

- 方案是否符合已知约束？
- 纯软件逻辑是否按预期工作？
- 当前工程能否为精确目标生成产物？
- 产物能否安全写入目标设备？
- 真实硬件是否满足功能、时序、异常和恢复要求？

任何一层通过都不能替代下一层。

## 验证阶梯

```text
Context Review
    ↓
Static / Host Validation
    ↓
Target Build
    ↓
Program / Load
    ↓
Hardware Observation
    ↓
Regression and Context Update
```

### 1. Context Review

检查目标 MCU、板卡修订、SDK、工具链、构建配置、引脚、外设和验收条件是否明确。若关键事实冲突，相关验证停止。

### 2. Static / Host Validation

适用于无需目标硬件即可验证的内容：

- 格式化、静态检查和编译期约束；
- 协议编解码、状态机和算法的主机测试；
- 配置 schema、生成器和日志解析工具测试；
- 边界输入、超时和错误恢复路径分析。

通过这一层只能说明对应软件逻辑，不代表目标固件已构建。

### 3. Target Build

使用项目原生入口和精确配置执行生成、编译和链接，记录：

- 源码版本与相关工作区状态；
- SDK、工具链、目标与构建命令；
- 返回状态、第一条关键错误和新增告警；
- Flash/RAM、section 或 map 变化；
- 产物路径、大小和哈希。

只有当前命令真实执行成功，才能标记 `BUILD PASSED`。

### 4. Program / Load

烧录不是自动步骤。执行前确认：

- 设备、MCU、板卡修订和接口电压；
- 产物对应当前目标和构建记录；
- 地址、分区、BootLoader、校准区和保护状态；
- 擦除范围、失败恢复方法和人工批准。

烧录成功只证明传输和校验，不等于功能通过。

### 5. Hardware Observation

每个观察必须对应验收条件，并说明证据来源：

- 串口日志：端口、波特率、抓取窗口、原始片段；
- 调试器：设备参数、连接方式、PC/SP、fault 或寄存器状态；
- 协议：请求、响应、时间范围、重试和错误码；
- 仪器：探测点、量程、采样条件、负载和观察值；
- 人工观察：操作步骤、预期、实际现象和不确定性。

功能正常路径之外，还应根据任务覆盖超时、断连、错误输入、复位和恢复。

### 6. Regression and Context Update

重新运行受影响的已有检查。只有当前版本已经复验、并且后续任务仍然适用的事实，才写回长期上下文。

## 状态模型

验收项状态：

- `Verified`：当前版本完成该验收项要求的全部检查；
- `Implemented, not rerun`：完成修改，但没有在当前环境复验全部检查；
- `Planned`：尚未实现；
- `Illustrative`：仅解释流程；
- `Blocked`：缺少事实、工具、设备、权限或决定。

任务级构建状态：

- `BUILD PASSED`
- `BUILD FAILED`
- `BUILD NOT RUN`

任务级硬件状态：

- `HARDWARE PASSED`
- `HARDWARE FAILED`
- `HARDWARE NOT RUN`

硬件相关验收项只有在命名设备上运行并满足条件后才能标记 `Verified`。仿真、构建或主机测试不能替代 `HARDWARE PASSED`。

## 证据最小集

每轮验证至少回答：

| 问题 | 需要记录 |
|---|---|
| 验证了什么 | 验收条件和范围 |
| 验证哪个版本 | 源码修订、相关工作区状态、产物身份 |
| 在什么目标上 | MCU、板卡修订、配置和连接方式 |
| 如何验证 | 精确命令、操作步骤和参数 |
| 得到什么 | 返回状态、原始输出或可定位观察 |
| 没验证什么 | 跳过阶段、原因、剩余风险和下一步 |

敏感内容应脱敏，但不能把脱敏后的概括冒充原始证据。

## 失败闭环

失败不是流程终点，而是下一轮输入：

1. 保留第一条可行动错误和必要上下文；
2. 判断失败属于上下文、推理、工具、构建还是硬件阶段；
3. 回退到最早受影响阶段；
4. 只修改一个可以否定或确认当前假设的变量；
5. 重新执行相关验证阶梯；
6. 在完成前报告未覆盖的风险。

验证的价值不在于尽快得到“通过”，而在于确保每个结论都能被重复、定位和修正。
