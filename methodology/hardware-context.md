# Hardware Context：把硬件事实变成 Agent 输入

## 目的

Hardware Context 不是一段概括性项目介绍，而是 Agent 开始推理前必须读取的事实集合。它要回答三个问题：

1. 当前修改针对哪一个确定的硬件和软件目标？
2. 哪些约束会影响架构、代码、构建或验证？
3. 哪些信息仍然未知，因而禁止继续哪些动作？

上下文的目标不是一次收集全部资料，而是为当前任务提供足够、可追溯且不过期的最小事实集。

## 上下文组成

| 类别 | 至少记录 | 主要来源 |
|---|---|---|
| 目标身份 | MCU 完整型号、板卡名称与修订、样机标识范围 | 原理图、PCB/板卡文件、芯片丝印、项目配置 |
| 电气边界 | 供电与 I/O 电压、上电顺序、复位、外部负载、安全限制 | 原理图、器件手册、实际测量 |
| 时钟与资源 | 时钟源、目标频率、Flash/RAM、外设实例、DMA/IRQ 占用 | Reference Manual、链接脚本、生成配置、工程代码 |
| 引脚与连接 | 引脚、复用功能、上下拉、极性、总线地址和外设连接 | 原理图、pin map、板级配置 |
| 软件目标 | SDK/HAL 和版本、工具链、构建目标、启动文件、链接布局 | 锁定文件、构建文件、编译输出、SDK 头文件 |
| 工程结构 | 目录职责、层级依赖、初始化顺序、生成代码边界 | 当前源码、工程配置、项目级说明 |
| 运行约束 | 实时性、缓冲区、并发、协议、错误恢复、持久化要求 | 需求、已有实现、真实故障记录 |
| 验证条件 | 构建入口、烧录方式、串口、调试器、仪器、验收信号 | 项目脚本、设备连接说明、测试记录 |

## 事实层级

出现冲突时，按以下顺序判断：

1. 当前板卡对应的原理图、PCB 文件和已验证网络表；
2. 精确芯片型号的 Datasheet、Reference Manual、Programming Manual 和 Errata；
3. 外部器件与开发板官方资料；
4. 当前版本 SDK/HAL 头文件、链接脚本、生成配置和官方示例；
5. 当前工程代码、构建输出以及带条件的真实硬件观察；
6. 历史文档或人工记忆。

低层级信息不能静默覆盖高层级事实。若来源相互矛盾，应记录冲突和版本，停止依赖该事实的实现或设备操作。

## Agent 可读取格式

上下文可以使用 Markdown、YAML 或仓库已有格式，但至少区分以下字段：

```yaml
target:
  mcu: "[TO BE PROVIDED]"
  board_revision: "Unknown"
software:
  sdk: "[TO BE PROVIDED]"
  sdk_version: "Unknown"
  build_command: "Unknown"
hardware:
  voltage_domain: "Unknown"
  facts: []
unknowns:
  - "当前板卡修订"
  - "目标固件对应的链接布局"
constraints:
  - "未确认目标、板卡修订和接口电压前禁止烧录"
validation:
  build: "Unknown"
  hardware: "Unknown"
```

示例中的具体值不能直接复制到另一个项目。Agent 必须重新核对目标和来源。

## 处理未知信息

未知不是失败，也不能被默认值掩盖。按影响分为三类：

- **不影响当前步骤**：保留为 `Unknown`，继续只读分析或独立的软件工作；
- **影响实现正确性**：暂停相关代码修改，指出需要的资料或工程位置；
- **影响设备安全或不可逆状态**：禁止供电、烧录、寄存器写入或物理操作，等待人工确认。

引脚、时钟、电压、寄存器地址、DMA 映射、Flash 分区、Option Bytes 和外部器件时序不得由 Agent 猜测。

## 上下文生命周期

1. **任务开始**：从工程和硬件资料生成当前快照，不照搬旧项目上下文。
2. **分析阶段**：把事实、假设、未知和冲突分开记录。
3. **执行阶段**：工具输出产生新事实时，附带命令、版本和时间范围。
4. **验证阶段**：只有通过当前版本复验的结论才升级为已验证事实。
5. **任务结束**：将长期有效的事实写回项目上下文；一次性故障和未证实推测留在任务记录。

## 完成条件

当 Agent 可以明确说明目标身份、软件版本、修改边界、构建入口、验证路径和剩余未知项时，Hardware Context 才足以进入实现。它不要求所有字段已知，但要求每个未知项的影响已经被识别。
