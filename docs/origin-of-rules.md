# Origin of Embedded AI Rules

## Purpose

本文解释 `AGENTS.md` 中各类工程约束从何而来。它不是项目履历、客户案例或代码实现说明，而是对真实嵌入式研发中反复出现的问题进行去敏感化归纳，说明经验如何转化为 AI Agent 可执行、可验证的规则。

统一追溯路径为：

`工程来源 → 失败风险 → 沉淀规则 → Agent 行为 → 验证证据`

`AGENTS.md` 保存可在任务中直接应用的约束，本文只解释规则来源。使用这套实践模板时，具体动作以 `AGENTS.md` 为准；这不代表它是一套通用标准或完整 Agent 系统。

## 1. Hardware Truth

### 工程来源

实际 MCU 开发中，引脚复用、时钟树、DMA 映射、中断向量、Flash 布局和外设电气条件都由精确芯片、板卡修订与 SDK 版本共同决定。相似型号、旧版本示例或经验记忆不能替代当前工程事实。

### 失败风险

- 使用错误的引脚、时钟或 DMA 通道，代码可以通过编译但设备不工作；
- 忽略板卡电压、极性或启动顺序，可能造成不可逆设备风险；
- 将其他 SDK 版本的接口直接套用，产生隐蔽的兼容性问题；
- AI 用“常见配置”填补缺失信息，使假设看起来像事实。

### 沉淀规则

`Hardware Truth > Software Assumption`

硬件事实必须按原理图、精确器件资料、当前 SDK/HAL、工程文件和实测证据的顺序确认。缺失或冲突的关键事实必须保持为 `Unknown`，不得猜测。

### Agent 行为与验证

Agent 在改动前建立 Hardware Context，区分事实、假设、未知和冲突。涉及供电、烧录、Option Bytes、Flash 分区或外设写操作时，必须先确认目标与安全边界。验证记录应引用资料版本、工程配置、命令输出或真实观测，而不是只给出推理结论。

## 2. Resource Classification and Static Design

### 工程来源

国产 MCU 适配和资源受限项目常同时面对 SDK 示例不足、RAM/Flash 紧张、外设资源冲突以及工具链差异。相同架构在不同资源等级的设备上并不一定成立。

### 失败风险

- 在小内存目标上照搬动态分配、复杂中间层或不受限缓存；
- 未核对中断、DMA 和定时器占用便增加驱动；
- 为追求通用性引入超过当前交付需求的抽象；
- 把 SDK 缺口误判为业务逻辑问题，重复修补。

### 沉淀规则

先按资源条件和联网能力分类，再选择执行模型、内存策略和架构层级；默认采用静态、可界定、可恢复的设计。未知资源不能被乐观估算覆盖。

### Agent 行为与验证

Agent 必须在任务合同中记录 MCU、内存、外设和 SDK 条件，解释架构选择与不选方案。构建后检查 Flash/RAM 占用、链接布局和静态缓冲区边界；未获得数据时明确记录未验证。

## 3. Architecture Rules

### 工程来源

多个嵌入式项目在功能持续增加后，容易出现应用逻辑直接操作寄存器、协议与传输耦合、板级配置散落、设备差异通过条件编译不断扩张等问题。

### 失败风险

- 新增设备或协议时修改多个无关模块；
- 测试无法隔离传输、协议和业务行为；
- 更换 MCU 或 SDK 时影响范围不可预测；
- AI 在没有边界的工程中重复实现能力或跨层修改。

### 沉淀规则

优先维持：

`Application → Middleware / Service → Driver → BSP → Hardware`

传输、协议、设备描述和产品行为分别建模；抽象层只在存在真实变化轴或复用需求时增加，避免为“可能的未来”构建平台。

### Agent 行为与验证

Agent 先解释现有模块职责、依赖方向和生成代码边界，再给出最小修改范围。验证不仅检查功能结果，还检查依赖是否反向、硬件事实是否泄漏到业务层，以及是否引入未使用的抽象。

## 4. State Machine and Fault Recovery

### 工程来源

工业设备长期运行时会遇到网络断开、CAT1/LoRa 链路波动、传感器超时、外设异常、服务器不可达以及升级中断。正常路径代码不能代表设备在异常条件下可用。

### 失败风险

- 隐式状态散落在标志位、延时和回调中，故障序列无法复现；
- 无限重试、固定短周期重连或直接重启造成拥塞和故障循环；
- 将链路建立、会话建立和业务送达混为一个“已连接”状态；
- 恢复后未清理资源或未保留诊断证据。

### 沉淀规则

使用显式状态和事件，例如：

`INIT → IDLE → RUNNING → ERROR → RECOVERY`

每个状态定义入口、退出、超时、重试上限和可观察事件；恢复策略采用有界重试、退避、降级与可诊断失败，不用 watchdog 代替根因处理。

### Agent 行为与验证

Agent 在实现重连或恢复前先输出状态/事件模型和失败策略。验证至少覆盖正常路径、超时、断链、重复事件和恢复后资源状态，并用串口日志、调试器状态或真实设备现象重建时序。

## 5. Workflow and Tool Boundaries

### 工程来源

SDK 优化与开发工具实践中，重复环境配置、工程模板创建、编译日志不清晰以及固件升级步骤容易出错。开发效率问题往往来自流程摩擦，而不只是缺少新功能。

### 失败风险

- Agent 未确认本地工具链便替换构建系统；
- 编译命令、生成步骤和环境版本不可复现；
- 烧录、擦除、分区或升级动作缺少明确目标与授权；
- 自动化掩盖失败输出，无法定位问题发生在哪一步。

### 沉淀规则

优先使用仓库原生工作流；把工具输入、输出、失败条件和副作用写成显式契约。只读分析与工程修改可以逐步推进，设备状态变更和不可逆动作必须经过安全检查与授权边界。

### Agent 行为与验证

Agent 记录准确命令、工作目录、工具版本、退出码和关键错误。环境缺失时给出 `BUILD NOT RUN`，而不是推断成功；烧录或 OTA 条件不完整时停止对应动作，但可继续不依赖设备状态的分析。

## 6. Evidence-Driven Development

### 工程来源

嵌入式问题不能只通过阅读代码判断。编译成功只能说明某个构建目标成立，不能证明引脚、电气、时序、通信、功耗或故障恢复在真实设备上符合预期。

### 失败风险

- 将静态检查、生成代码或“逻辑看起来正确”报告为构建通过；
- 将构建通过报告为功能完成；
- 只记录最终现象，不保留命令、日志、调试器状态和测试条件；
- 修改失败后继续扩大范围，导致原因不可追踪。

### 沉淀规则

`Build Passed ≠ Hardware Validated`

证据按阶段分开：分析证据、工具执行证据、构建证据和硬件验证证据。每个结论只覆盖其证据能够支持的范围。

### Agent 行为与验证

Agent 必须给出精确验收状态：`Verified`、`Implemented, not rerun`、`Planned`、`Illustrative` 或 `Blocked`，并独立报告 Build 与 Hardware 状态。硬件验证记录目标板、固件、连接方式、输入条件、预期行为、实际行为和未完成项；失败时优先收窄原因，而不是宣称闭环。

## 7. Rule-Maintenance Boundary

新经验不能直接写入通用规则集。维护这些实践规则时应确认：

1. 问题是否在不同任务中重复出现，而不是一次性特例；
2. 规则能否改变 Agent 的具体行为或验证要求；
3. 规则是否依赖未披露的项目细节；
4. 规则是否会错误限制资源等级、SDK 或架构不同的工程；
5. 是否存在可观察证据判断规则已执行。

只有满足以上条件的经验才进入 `AGENTS.md`。单个项目的具体命令、引脚和版本信息应留在项目级上下文中，不应提升为跨项目事实。
