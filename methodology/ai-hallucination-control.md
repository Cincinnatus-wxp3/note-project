## 问题定义

嵌入式场景中的 AI 幻觉不只表现为“API 不存在”。更常见的风险是：代码在语法上合理，却混用了芯片系列、SDK 版本、板卡引脚、寄存器定义、时序条件或工程初始化顺序。

控制幻觉的目标不是要求 AI 永不出错，而是让每一个推断：

- 能追溯到来源；
- 能被工具验证；
- 在证据不足时可以停止；
- 失败后能带着新证据重新推理。

## 四类高风险错配

| 类型 | 常见表现 | 必须核对 |
|---|---|---|
| 硬件错配 | 猜测引脚、时钟、电压、DMA、IRQ 或外设连接 | 原理图、精确型号手册、板级配置 |
| SDK 错配 | 使用另一版本 API、配置项、组件名称或初始化方式 | SDK 版本、头文件、构建清单、官方迁移说明 |
| 工程错配 | 忽略生成代码边界、依赖方向、启动顺序或链接布局 | 当前目录、调用链、构建文件、链接脚本 |
| 验证错配 | 把静态分析或编译结果描述成设备运行结果 | 实际命令、产物身份、串口/调试器/仪器证据 |

## 事实—假设—未知模型

Agent 在给出方案前必须把信息分成三类：

- **Fact**：存在可定位来源，例如文件、行号、文档章节、工具输出或硬件记录；
- **Assumption**：为了推进软件设计采用的可逆判断，必须标明验证方式；
- **Unknown**：缺少依据，且不能由常识或相似项目补齐。

硬件事实不能降级为隐含假设。未知项影响安全、存储布局或外设绑定时，相关动作必须 `Blocked`。

## 控制流程

### 1. Grounding：先检索，再回答

- 读取当前工程的 `AGENTS.md`、构建文件、配置、头文件和相关实现；
- 确认精确 MCU、SDK 和板卡版本；
- 沿定义、引用和调用链理解现有行为；
- 优先复用当前项目中已验证的模式，不凭模型记忆补 API。

### 2. Constraint：把允许范围写进任务契约

明确：

- 要解决的问题和可观察结果；
- 允许修改的文件、模块和接口；
- 不得改动的生成代码、协议兼容性和安全边界；
- 内存、实时性、并发和恢复约束；
- Build 与 Hardware 的独立验收条件。

### 3. Decomposition：缩小单轮推理跨度

每轮只完成一个可构建、可观察的切片。驱动接入可以拆为：

1. 资源和引脚事实确认；
2. 最小初始化与读写接口；
3. 协议或数据解析；
4. 超时和恢复；
5. 上层集成与回归。

切片越小，工具结果越容易定位是支持还是否定当前假设。

### 4. Tool-grounding：用实际输出纠正模型

- 编译器验证 API、类型、符号和链接关系；
- map/size 输出验证存储布局和资源变化；
- 主机测试验证纯逻辑和异常输入；
- 串口、J-Link/GDB/OpenOCD 验证启动、fault 和运行状态；
- 仪器验证软件日志无法证明的电气和时序行为。

工具没有执行时，Build 必须使用 `BUILD NOT RUN`，硬件验证必须使用 `HARDWARE NOT RUN`，不能用推理补齐结果。

### 5. Feedback：把失败转换成下一轮输入

失败记录至少包含：

- 精确命令、目标、版本和返回状态；
- 第一条可行动错误或实际硬件现象；
- 当前假设；
- 哪个阶段需要回退；
- 下一轮只验证什么。

不要在没有新证据时重复生成不同代码版本。

## 风险分级与停止策略

- **低风险**：命名、注释、纯逻辑整理；可通过代码审查和主机测试推进。
- **中风险**：驱动 API、并发、内存和协议修改；要求当前目标构建和专项验证。
- **高风险**：供电、时钟、电机/继电器等执行器、Flash 布局、BootLoader、OTA、Option Bytes、熔丝；要求精确硬件事实、恢复方案和人工批准。

如果证据不足，只停止受影响阶段。安全的工程检索、基线建立和纯软件分析仍可继续。

## 常见反模式

- 从相似芯片示例复制寄存器配置但未核对精确型号；
- 只给 AI 一个报错截图，不提供 SDK 版本、构建命令和第一条错误；
- 在一次修改中同时更换 SDK、重构架构并新增功能；
- 为获得绿色构建而关闭告警或绕过检查；
- 使用“应该可以”“理论上已修复”代替状态和证据；
- 把示例日志、合成数据或历史结果描述为当前设备结果；
- 将未验证的 AI 输出写入长期项目规则。

## 输出要求

一次受控推理至少输出：

1. 已确认事实及来源；
2. 可逆假设及验证方法；
3. 未知项和它们阻塞的动作；
4. 最小改动范围；
5. 计划调用的工具；
6. Build 与 Hardware 的独立状态；
7. 失败后的回退阶段和下一步。
